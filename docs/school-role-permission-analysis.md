# วิเคราะห์บทบาทและสิทธิ์โรงเรียน พร้อมชุดข้อมูลจำลอง

ตรวจจากโค้ดและฐานข้อมูลท้องถิ่นวันที่ 15 ตุลาคม 2569

## ข้อสรุป

> **อัปเดต 16 ต.ค. 2569:** ระบบเปลี่ยนเป็น "หน้าบทบาทและสิทธิ์เป็นแหล่งสิทธิ์เดียว" แล้ว preset ของบทบาทโรงเรียน เงื่อนไข OR ตามบทบาท และสิทธิ์รายสมาชิกไม่เพิ่ม/ลดสิทธิ์อีก บทบาทโรงเรียนกำหนดเฉพาะขอบเขตนักเรียน ทุกโมดูลมีครบ 7 การกระทำ (รวม `school_staff` และ `school_workflows` ที่แยกจาก `school.*`) ข้อ "ความซ้ำซ้อนและข้อควรแก้" ด้านล่างจึงได้รับการแก้แล้ว ยกเว้นขอบเขต "ไม่มีบทบาทโรงเรียน" ที่ยังเห็นทั้งหน่วยงานโดยตั้งใจ รายละเอียดความหมายแต่ละช่องดู `docs/unit-permission-matrix.md` และย้ายข้อมูลเดิมด้วย `migrate:roles-page-only`

ปรับหน้าจัดการแล้ว: `/admin/roles` เป็นจุดเดียวสำหรับเลือกหน่วยงาน จัดการสิทธิ์ที่ใช้งานจริง เพิ่ม/ลบบทบาท และจัดการสมาชิก พร้อมส่วนผู้ดูแลระบบแยกต่างหาก หน้าหน่วยงานเหลือการจัดโครงสร้างและตั้งค่าบริการ ส่วนหน้าบทบาทโรงเรียนเดิม `/admin/school/roles` เปลี่ยนทางไปที่ `/admin/users` ซึ่งผู้ดูแลโรงเรียน (`can_manage_staff`) เข้าได้โดยไม่เห็นส่วนผู้ดูแลระบบ

รายการบทบาทในหน้า Roles มาจากชุดสิทธิ์หรือสมาชิกของหน่วยงานที่เลือก ไม่อ่านแม่แบบกลางมาใช้แก้สิทธิ์ การลบบทบาทจากหน่วยงานจะลบเฉพาะชุดสิทธิ์ของหน่วยงานนั้น และปฏิเสธหากยังมีสมาชิกอ้างอิง ไม่ลบนิยามบทบาทที่หน่วยงานอื่นอาจใช้อยู่ System Admin ไม่ปรากฏเป็นบทบาทสิทธิ์หน่วยงาน

การรวมหน้าไม่เปลี่ยนนโยบายขอบเขตข้อมูลเดิม: ผู้ดูแลโรงเรียนยังจัดการสมาชิกโรงเรียนได้ แต่การแก้ชุดสิทธิ์หน่วยงานและบัญชีผู้ดูแลระบบยังต้องเป็น System Admin ข้อวิเคราะห์เรื่อง preset ในโค้ดและ explicit deny ด้านล่างยังเป็นข้อจำกัดของชั้นอนุญาตที่คงอยู่

แม่แบบกลางกับสิทธิ์รายหน่วยงานแยกหน้าที่กันได้ แต่ระบบปัจจุบันยังมีสิทธิ์จากบทบาทโรงเรียนเพิ่มเข้ามาอีกชั้น จึงมีความซ้ำซ้อนจริงระหว่าง **สิทธิ์หน่วยงาน** กับ **ชุดสิทธิ์ประจำบทบาทโรงเรียน** การเอาเครื่องหมายออกในหน้าสิทธิ์หน่วยงานจึงไม่ได้แปลว่าปิดสิทธิ์นั้นเสมอไป

ชุดข้อมูลจำลองและเครื่องมือตรวจสอบยังใช้งานได้ การปรับครั้งนี้รวมหน้าจัดการ โดยไม่ได้ย้ายหรือเขียนทับสิทธิ์หน่วยงานเดิม

## แต่ละหน้าทำอะไร

| หน้า/องค์ประกอบ          | เก็บที่                                                              | หน้าที่และพฤติกรรมจริง                                                                                          |
| ------------------------ | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| แม่แบบบทบาทและสิทธิ์     | `roles`, `role_permissions`                                          | รายชื่อบทบาทและชุดสิทธิ์กลาง ผู้ดูแลระบบจัดการ ไม่ถูกนำมาใช้เป็นสิทธิ์หน่วยงานโดยอัตโนมัติ                      |
| บทบาทและสิทธิ์ในหน่วยงาน | `organization_role_permissions`, `organization_role_permission_sets` | สิทธิ์ตามคู่หน่วยงาน+บทบาท บทบาทเดียวกันต่างหน่วยงานมีสิทธิ์ต่างกันได้                                          |
| สมาชิกหน่วยงาน           | `organization_memberships`                                           | ระบุว่าบัญชีเป็นสมาชิกหน่วยงานใด และใช้บทบาทใดในหน่วยงานนั้น                                                    |
| บทบาทและสิทธิ์โรงเรียน   | `school_staff_roles`                                                 | ระบุหน้าที่จริงหนึ่งบทบาทต่อคนต่อโรงเรียน เช่น ครูประจำชั้น/แนะแนว/ผู้ปกครอง และเพิ่มชุดสิทธิ์จาก preset ในโค้ด |
| การมอบหมายห้อง/นักเรียน  | `school_classroom_teachers`, `school_student_guardians`              | จำกัดว่านักเรียนคนใดอยู่ในขอบเขตของครูหรือผู้ปกครอง                                                             |
| สิทธิ์ข้อมูลเฉพาะสมาชิก  | `organization_membership_data_permissions`                           | อนุญาต/ปฏิเสธ `pii.view` และ `clinical.view` เพิ่มเติม โดยรายการ explicit ประมวลผลหลัง snapshot เดิม            |
| บทบาทระดับระบบ           | `user_system_roles` และ legacy `users.role_id=1`                     | System Admin มีสิทธิ์ข้ามขอบเขตตามโค้ด แยกจากบทบาทผู้ดูแลโรงเรียน                                               |

ประเภทครูที่แก้ไขชื่อได้เป็นข้อมูลจัดหมวด ไม่ใช่ตัวให้สิทธิ์ เช่น การสร้างประเภทชื่อ “ครูแนะแนว” อย่างเดียวไม่ได้ให้สิทธิ์ดูข้อมูลเชิงลึก ต้องกำหนดบทบาทโรงเรียนด้วย

แม่แบบกลางเคยถูกคัดลอกมาเป็น snapshot ในสคริปต์ย้ายระบบ `migrateOrganizationPermissions.js` แต่เส้นทางใช้งานปัจจุบันอ่านสิทธิ์รายหน่วยงานโดยตรง ไม่มี fallback ไปหาแม่แบบ และในหน้าสิทธิ์หน่วยงานปัจจุบันยังไม่มีขั้นตอนนำเข้าแม่แบบแบบเลือกใช้

หน้าแม่แบบไม่แสดง `school_guardian`, `school_import_staff` และบทบาทตรวจสอบ “มีแม่แบบแต่ไม่มีสิทธิ์หน่วยงาน” เพราะสองรายการแรกเป็นรหัสบัญชีภายในที่ขั้นตอนโรงเรียนยังใช้งาน ส่วนรายการสุดท้ายมีไว้ตรวจกรณีไม่ได้รับสิทธิ์ ทั้งสามจึงไม่ใช่แม่แบบที่ผู้ดูแลต้องตั้งค่าสำหรับงานประจำ การนำออกจากหน้านี้ไม่ลบข้อมูลหรือเปลี่ยนสิทธิ์ของบัญชีที่อ้างอิงอยู่

## ลำดับการคำนวณปัจจุบัน

1. ตรวจบัญชีและสมาชิกของหน่วยงานที่เลือก
2. อ่านสิทธิ์จาก `organization_role_permissions` โดยใช้ทั้ง organization ID และ role ID
3. รวมสิทธิ์จาก preset ของ `school_staff_roles` ใน `schoolRolePermissions.js`
4. ใช้สิทธิ์ข้อมูลส่วนบุคคล/สุขภาพเฉพาะสมาชิกทับผลที่ได้
5. `schoolAccess.js` คำนวณขอบเขตโรงเรียน ห้อง นักเรียนประจำ และนักเรียนที่ผูกกับผู้ปกครอง รวมถึงความสามารถบางอย่างจากบทบาทโดยตรง
6. API ตรวจความสามารถและขอบเขตข้อมูล ส่วน `privateDisclosure` ทำการปกปิดข้อมูลตามเงื่อนไข

ข้อยกเว้นสำคัญ: ผู้ปกครองล้างสิทธิ์กว้างจากบทบาทหน่วยงานก่อนใช้ preset ผู้ปกครอง และถูกจำกัดการเขียนข้อมูล เหลือเฉพาะนักเรียนที่ผูกไว้ ผู้ดูแลระบบมีทางผ่านแยกต่างหาก

## สิทธิ์หน่วยงานที่เพิ่ม 16 ต.ค. 2569

เดิมงานจัดการบุคลากร/ผู้ปกครอง และงานคัดกรองติดตามของโรงเรียนผ่านได้เฉพาะบทบาทโรงเรียน `admin`/`mental_admin` หน้าบทบาทและสิทธิ์จึงมอบให้บทบาทหน่วยงานอื่นไม่ได้ เพิ่มสิทธิ์ที่มอบได้สำหรับหน่วยงานประเภทโรงเรียน (ทั้งหน้าเว็บและ `allowedKeysFor` ฝั่งเซิร์ฟเวอร์):

| สิทธิ์                    | ครอบคลุม                                                                                                | ตัวตรวจฝั่งเซิร์ฟเวอร์                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `school_staff.manage`     | มอบบทบาทในโรงเรียน นำเข้าครู สร้าง/ผูกบัญชีผู้ปกครอง (มอบบทบาทผู้ดูแลโรงเรียนได้)                       | `canManageStaffAt` ใน `schoolInsightRoutes`, `schoolTeacherImportRoutes` |
| `school_workflows.manage` | รอบคัดกรอง คัดกรองซ้ำ เกณฑ์เสี่ยง ตั้งค่าคำแนะนำ เลื่อนชั้น การลงทะเบียน และการเก็บข้อมูลหลังจบการศึกษา | `canManageWorkflowsAt` ใน `schoolWorkflowRoutes`                         |

บทบาทโรงเรียน `admin` และ `mental_admin` ได้ทั้งสองสิทธิ์ผ่าน preset เหมือนเดิม เกณฑ์เสี่ยงยังต้องมีสิทธิ์ดูข้อมูลสุขภาพร่วมด้วย คอลัมน์ `permission_key` เป็น VARCHAR จึงไม่ต้องย้ายฐานข้อมูล หน่วยงานที่ต้องการใช้ให้ System Admin ติ๊กสิทธิ์ใหม่ในหน้า `/admin/roles`

## โครงสร้างที่แนะนำ

เก็บแม่แบบกลางไว้เป็นชุดตั้งต้นที่เลือกคัดลอกได้ ส่วนสิทธิ์รายหน่วยงานเป็นค่าที่ใช้งานจริง การแก้แม่แบบไม่เปลี่ยนสิทธิ์หน่วยงานที่คัดลอกไปแล้ว ควรมีปุ่ม “นำเข้าแม่แบบ” พร้อมดูความต่างก่อนบันทึก

บทบาทโรงเรียนควรระบุหน้าที่และขอบเขตข้อมูล โดยการกำหนดบทบาทสามารถเสนอชุดสิทธิ์ตั้งต้นได้ แต่ไม่ควรเติม permission กลับอย่างซ่อนเร้นทุกครั้งที่ร้องขอ API หากมีสิทธิ์ขั้นต่ำที่ระบบบังคับจริง หน้าตั้งค่าต้องแสดงว่าเป็นสิทธิ์บังคับและระบุเหตุผล

กฎที่แนะนำคือ **สมาชิกยังใช้งานได้ + มีสิทธิ์การกระทำ + อยู่ในขอบเขตนักเรียน + มีสิทธิ์ข้อมูลประเภทนั้น + ไม่ถูกปฏิเสธโดยตรง** โดยกำหนดข้อยกเว้น System Admin และผู้ปกครองให้ชัดเจน

ควรทำหน้าดู “สิทธิ์จริงของสมาชิก” ที่บอกได้ว่าแต่ละสิทธิ์มาจากหน่วยงาน แม่แบบที่เคยคัดลอก หรือข้อจำกัดรายบุคคล พร้อมตัวอย่างจำนวนห้อง/นักเรียนที่เข้าถึงได้ ก่อนรวมหน้าตั้งค่าหรือย้ายข้อมูลใด ๆ

## ชุดจำลองที่เพิ่มแล้ว

ใช้โรงเรียนเดิมใน **หน่วยงาน 2 โรงเรียน 1** หน่วยงาน 4 เป็นหน่วยงานหลัก จึงไม่ได้เพิ่มสิทธิ์การทำงานให้หน่วยงานหลัก ชื่อสมาชิกและแม่แบบบทบาทแสดงเป็นภาษาไทยตามหน้าที่ ชื่อผู้ใช้สำหรับเข้าสู่ระบบขึ้นต้น `school.`

## วิธีใช้และหลักฐาน

เปิด `/admin/school/roles` ในหน่วยงานโรงเรียน 2 เพื่อดูรายการบทบาทจำลอง ส่วนการเทียบแม่แบบกับสิทธิ์หน่วยงานใช้บทบาทชื่อภาษาไทย เช่น “ผู้ดูแลโรงเรียน” และ “ครูประจำชั้น” ในสองหน้าตั้งค่า ผู้ปกครองใช้บทบาทระบบเดิม `school_guardian` เพื่อคงพฤติกรรมเมื่อถอนบทบาท

- บัญชีและรหัสผ่าน: `backup/school-role-demo-accounts.csv`
- รายการข้อมูลที่เพิ่มและค่าก่อนแก้สถานะนักเรียนประจำ/จบการศึกษา: `backup/school-role-demo-manifest.json`
- ผลตรวจสิทธิ์ที่คำนวณจริง: `backup/school-role-demo-verification.json`
- ผลตรวจ API: `backup/school-role-demo-api-verification.json`

ไฟล์เหล่านี้อยู่ใน gitignore รหัสผ่านสุ่มแยกบัญชี ไม่แสดงในรายงานหรือ console อีเมลเป็น `example.test` สำหรับข้อมูลจำลอง รับ OTP จริงไม่ได้ หากต้องการทดสอบล็อกอินจริงให้ผู้ดูแลเปลี่ยนอีเมลของบัญชีจำลองเป็นอีเมลทดสอบที่รับได้ตามกระบวนการเดิม ไม่ได้ข้ามการยืนยันตัวตน

```powershell
pnpm --filter suthiecare-api seed:school-roles-demo
pnpm --filter suthiecare-api verify:school-roles-demo
```

สคริปต์ทำงานเฉพาะฐานข้อมูลท้องถิ่น ต้องมี manifest ของชุดโรงเรียนเดิม เมื่อมี manifest ของชุดบทบาทแล้ว การเรียกซ้ำจะตรวจสอบชุดเดิมโดยไม่สร้างซ้ำ ไม่มีคำสั่งล้างข้อมูลหรือเปลี่ยนนโยบายสิทธิ์อัตโนมัติ

ผลตรวจ: 10 บัญชีผ่านการตรวจขอบเขต, API โรงเรียนจริง 166 จุดผ่าน รวมการเลื่อนชั้นและ retention แบบ dry run, ตรวจความขัดแย้ง policy เพิ่ม 2 กรณี และ unit tests ที่เกี่ยวข้อง 17 รายการผ่าน การตรวจ API ใช้เซิร์ฟเวอร์ loopback ชั่วคราว เชื่อม DB จริง ใช้ authorization/ขอบเขต/serializer จริง แต่ไม่ได้ทดสอบ session/OTP หรือการกดทุกหน้าในเบราว์เซอร์
