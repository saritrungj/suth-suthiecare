# Sidebar ตามบทบาทระดับระบบ

แยกบทบาทระดับระบบจากบทบาทสมาชิกของแต่ละหน่วยงาน โดยใช้ข้อมูลที่ `/api/me/authorization` ตรวจจากบัญชีในฐานข้อมูล ไม่ใช้บทบาทที่เก็บไว้ใน localStorage/sessionStorage หรือชื่อบทบาทสมาชิกหน่วยงานมาตัดสินเมนูระดับระบบ

| บทบาทระดับระบบ | เมนู Sidebar                                                          |
| -------------- | --------------------------------------------------------------------- |
| System Admin   | ทุกเมนูที่ใช้กับประเภทหน่วยงานที่เลือก รวมกลุ่มจัดการหลักของระบบ      |
| Admin          | เมนูงานตามสิทธิ์หน่วยงานและเมนูบัญชี ไม่มีเมนูจัดการหลักของระบบ       |
| Staff          | เฉพาะผู้มารับบริการ เมื่อมี `patient_members.view` ในหน่วยงานที่เลือก |

กลุ่มจัดการหลักของระบบประกอบด้วย หน่วยงานหลักและหน่วยงานย่อย, ผู้ดูแลระบบและเจ้าหน้าที่, บทบาทและสิทธิ์, และจัดการภาพแบนเนอร์ มี route guard สำหรับ System Admin ป้องกันการเปิดหน้าเหล่านี้ผ่าน URL โดย Admin/Staff

Staff ไม่เห็นเมนูเคส ฟอร์ม ส่งต่อ โรงเรียน ข้อมูลส่วนตัว หรือคู่มือใน Sidebar แม้มีบทบาท Admin ภายในหน่วยงาน ยังมีตัวเลือกหน่วยงานและปุ่มออกจากระบบ การดูและแก้ไขข้อมูลผู้มารับบริการใช้สิทธิ์ของหน่วยงานนั้นตามเดิม

หลังเข้าสู่ระบบเจ้าหน้าที่จะเข้า `/admin` และใช้บทบาทที่ API ตรวจแล้วเลือกหน้าเริ่มต้น Staff เข้า `/admin/members`; Admin/System Admin เข้าแดชบอร์ดตามเดิม

`system_role` เป็นฟิลด์เพิ่มเติมใน authorization response: `system_admin`, `admin`, `staff` หรือ `null` สำหรับบทบาทที่ยังไม่รู้จัก รองรับ response รุ่นเดิมผ่าน `authorization.user.role_id` (2=Admin, 3=Staff); การเป็น System Admin ต้องใช้ `is_system_admin` ที่ API ตรวจสอบ บทบาทที่ไม่รู้จักไม่ถูกยกระดับสิทธิ์

ขอบเขตครั้งนี้เป็นการปรับนโยบายเมนูและ route guard ของหน้าจัดการหลัก ไม่ได้ลบหรือเพิ่มสิทธิ์การทำงานในแต่ละหน่วยงาน ไม่แก้สมาชิกหรือบทบาทในฐานข้อมูล และไม่มี migration ใหม่

เฉพาะ System Admin มีตัวเลือก “ทุกหน่วยงาน” และได้รับรายการหน่วยงานทั้งหมด Admin/Staff ใช้เฉพาะ memberships แม้ role ภายในหน่วยงานจะเป็น SuperAdmin ตัว setter ตรวจค่าที่เลือกซ้ำ ไม่รับ `all` หรือหน่วยงานนอกสิทธิ์จากค่าที่เก็บไว้ ฝั่ง API ที่ผ่าน resolveContext ปฏิเสธ all/หน่วยงานอื่นด้วย 403

การตรวจสอบล่าสุด: frontend unit tests 43 ผ่าน, authorization API tests ใหม่ 6 ผ่าน (backend ทั้งชุด 87 ผ่าน 1 ข้าม), browser tests 10 ผ่านบน desktop/mobile ครอบคลุมสามบทบาท ตัวเลือกทุกหน่วยงาน การสลับหน่วยงาน session role ที่ไม่ตรงกับ API และการเปิด URL ของเมนูจัดการหลัก; production build ผ่าน

ดูช่องว่างความปลอดภัยของ API รุ่นเดิมและงาน PDPA ที่ยังเปิดอยู่ใน [security-audit.md](pdpa/security-audit.md); การแก้ Sidebar ไม่ใช่การรับรองสิทธิ์ทุก endpoint
