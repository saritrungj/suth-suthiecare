# ตรวจความปลอดภัยและ PDPA ของ SuthieCare

ตรวจวันที่ 3 ตุลาคม 2569 จากโค้ดใน workspace ปัจจุบัน ไม่อ่านค่าข้อมูลผู้รับบริการ ไม่ทดสอบโจมตี Production และไม่ส่งข้อความแจ้งเตือนจริง ข้อค้นพบด้านการจัดเก็บหมายถึงเส้นทางเขียนในโค้ด ไม่ใช่การยืนยันว่าทุกแถวในฐานข้อมูลเป็นข้อความปกติ

**ผล:** มี AES-256-GCM, HMAC สำหรับค้นหา, password hashing และการจำกัดหน่วยงานแล้ว แต่ยังมีช่องว่างสำคัญด้านข้อมูลสุขภาพ การเปิดเผยผ่าน Telegram และการตรวจสิทธิ์ API บางเส้นทาง จึงยังสรุปว่าระบบผ่าน PDPA ทั้งหมดไม่ได้

P1 = ควรแก้ก่อนใช้งานกับข้อมูลจริง/ขยายผู้ใช้หลายหน่วยงาน; P2 = งานเสริมความปลอดภัยและกระบวนการที่ต้องจัดลำดับต่อ คะแนนนี้เป็นลำดับความสำคัญจากการตรวจโค้ด ไม่ใช่คะแนนการละเมิดกฎหมายหรือหลักฐานว่าเกิดข้อมูลรั่วแล้ว

## จุดที่ควรแก้ก่อนใช้งานจริง

### P1-1: การแจ้งเตือน Telegram มีข้อมูลระบุตัวและข้อมูลสุขภาพ

[formRoutes.js:785](../../server/routes/formRoutes.js#L785) สร้างข้อความจากชื่อเต็ม โทรศัพท์พร้อม `tel:` ชื่อฟอร์ม คลินิก ความเสี่ยงและสถานะ ก่อนเรียก `dispatchTelegramAlert` ที่บรรทัด 873; [telegram.js:5](../../server/utils/telegram.js#L5) ใช้ `TELEGRAM_CHAT_ID` กลางชุดเดียว ไม่มีการเลือกรับตามหน่วยงาน

**ผลกระทบ:** ถ้าเปิดใช้งานจริง ผู้รับในกลุ่มกลางอาจได้รับข้อมูลของหลายหน่วยงาน; ชื่อฟอร์ม/ประเภทคลินิกอาจเผยเรื่องสุขภาพแม้ไม่ส่งคำตอบเต็ม การเข้ารหัสในฐานข้อมูลไม่ป้องกันข้อความนี้

**แนวแก้:** แจ้งเฉพาะว่ามีงานใหม่พร้อมรหัสอ้างอิงและลิงก์ที่ต้องล็อกอินและตรวจสิทธิ์หน่วยงาน งดชื่อ เบอร์ ชื่อประเมินเฉพาะโรค และผลความเสี่ยงในข้อความกลาง ถ้าต้องใช้ข้อมูลเพิ่ม ให้กำหนดปลายทางรายหน่วยงาน ผู้รับที่อนุญาต วัตถุประสงค์ ฐานกฎหมาย และประเมินผู้ให้บริการ/การส่งข้อมูลต่างประเทศจากข้อเท็จจริง

**ตรวจรับ:** ทดสอบด้วยข้อมูลจำลองว่า notification ไม่มี PII/สุขภาพ, ไม่ส่งผิดหน่วยงาน และลิงก์ไม่เปิดได้ด้วยรหัสอ้างอิงอย่างเดียว

### P1-2: เข้ารหัสคำตอบและข้อมูลคลินิกยังไม่สม่ำเสมอ

[formRoutes.js:62](../../server/routes/formRoutes.js#L62) ประเภทข้อมูลที่เข้ารหัสอัตโนมัติมี `national_id`, `full_name`, `phone_number`; การเขียนรายคำตอบที่บรรทัด 724 ยังอาศัย `questionTitles` จากคำขอ และสรุปที่บรรทัด 665–684 เลือกเข้ารหัสด้วยชื่อคีย์ ส่วนข้อมูลคลินิกที่ [caseRoutes.js:1125](../../server/routes/caseRoutes.js#L1125) เป็น JSON ปกติ; บันทึก/นัดหมายที่บรรทัด 149 และ 269 เป็นข้อความปกติ

การแก้คำตอบโดยเจ้าหน้าที่ [caseRoutes.js:450](../../server/routes/caseRoutes.js#L450) และผู้รับบริการ [patientRoutes.js:426](../../server/routes/patientRoutes.js#L426) ตรวจชื่อคำถามภาษาไทย ขณะที่การสร้างใช้ประเภทคำถามด้วย จึงมีเส้นทางที่อาจเขียนคำตอบกลับเป็น plaintext สำหรับคำถามที่เดิมเข้ารหัสจากประเภท ส่วน [storedAnswer.js](../../server/utils/storedAnswer.js) ถอดรหัสตามชื่อคำถามเช่นกัน

**แนวแก้:** ใช้ classification จาก schema ฟอร์มในเซิร์ฟเวอร์และตัวเก็บ/อ่านร่วมกันทุกเส้นทาง เข้ารหัส JSON ที่ประกอบด้วยข้อมูลสุขภาพทั้งคำตอบและสรุป ไม่ส่ง object/array เข้า `encrypt()` โดยตรง เพราะตัวเดิมใช้ `String(text)` ซึ่งอาจสูญเสียโครงสร้าง เพิ่ม envelope ที่มี version/key ID แยกข้อมูลใหม่ออกจาก legacy; backfill ด้วยการทดสอบอ่านกลับและแผน rollback ก่อนลงระบบจริง

**ตรวจรับ:** insert/edit/read/export ให้ข้อมูลเดิมครบทั้งตัวเลข false/0 array/object คำถามภาษาอังกฤษและคำถามไม่มีคำสำคัญ ข้อมูลใหม่ใน DB ต้องไม่เหลือสุขภาพ plaintext ใน summary ซ้ำอีกชุด; ห้ามสูญเสียข้อมูลเก่า

### P1-3: URL token ใช้กุญแจถอดรหัสข้อมูลร่วมกับฐานข้อมูล

[caseRoutes.js:1087](../../server/routes/caseRoutes.js#L1087) `/generate-token` ใช้ `encrypt(identity)` และ `/decode-token` ที่บรรทัด 1104 ถอดสิ่งที่ผู้เรียกส่งด้วยกุญแจเดียวกับข้อมูลใน DB ไม่มี purpose, expiry หรือการผูกฟอร์ม/หน่วยงาน/ผู้รับใน token นี้

**ผลกระทบ:** ผู้มีสิทธิ์เรียก decode และเข้าถึง ciphertext จากช่องทางใดก็ตามอาจใช้ endpoint นี้ถอดข้อมูลประเภทอื่นที่ใช้กุญแจเดียวกันได้ ข้อสรุปนี้มาจากโค้ด ยังไม่ได้ทดลองโจมตีจริง

**แนวแก้:** เปลี่ยนเป็น invitation token แบบสุ่ม เก็บเฉพาะ hash พร้อมผู้รับ/หน่วยงาน/ฟอร์ม อายุและการเพิกถอน ตรวจสิทธิ์การออก token กับเคสจริง และตรวจผู้ใช้เมื่อเรียกใช้ หากจำเป็นต้องใช้ signed token ให้แยกกุญแจและตรวจ purpose/audience/expiry อย่างเข้มงวด งดเลขบัตรใน URL และอย่าเปิดบริการถอด ciphertext ทั่วไป

### P1-4: ตรวจสิทธิ์ข้ามหน่วยงานยังมีเส้นทางเก่าที่หลุดการตรวจสัมพันธ์

1. POST [caseRoutes.js:125](../../server/routes/caseRoutes.js#L125) `/cases/:id/logs` ตรวจหน่วยงานจาก response ใน URL แต่ใช้ `master_case_id` จาก body ใส่ log และอัปเดต `mastercases.overall_risk` ที่บรรทัด 181 โดยไม่ตรวจว่า master นั้นผูกกับ response/หน่วยงานเดียวกัน ผู้มีสิทธิ์เขียนเคสของตนอาจกำหนด master ของหน่วยงานอื่นได้
2. [requestScope.js](../../server/authorization/requestScope.js) ยังไม่ครอบคลุม `/staffs`, `/services`, `/templates`, `/case-statuses`, `/status-options`; handlers อ่าน/แก้ตารางกลางโดยไม่จำกัดองค์กร เช่น [staffRoutes.js:6](../../server/routes/staffRoutes.js#L6), [caseRoutes.js:603](../../server/routes/caseRoutes.js#L603) และ `note_templates` ที่บรรทัด 801; cache services/status ก็ใช้คีย์กลาง การเขียน `/staffs` มี verifyToken แต่ไม่มี permission gate ใน handler และ policy write ของ index ไม่ครอบคลุมเส้นทางนี้

**แนวแก้:** derive master จาก response ที่ตรวจสิทธิ์แล้ว ไม่เชื่อ body; ตรวจความสัมพันธ์ staff/status/service/appointment ทุก foreign key และใช้ transaction งานอ้างอิงกลางต้องกำหนดให้ชัดว่าเป็น shared data ที่ System Admin แก้ได้ หรือเป็นข้อมูลหน่วยงานที่ query/write/cache ต้องใส่ organization scope ทั้งหมด ไม่เพิ่ม middleware อย่างเดียวโดยปล่อย SQL/cache เป็น global

**ตรวจรับ:** ผู้ใช้หน่วยงาน A อ่าน/แก้ B ไม่ได้แม้ปลอม body/query/header/รหัส record; บทบาทในหน่วยงานไม่ยกระดับระบบ; ทดสอบทั้ง endpoints ปัจจุบันและ alias รุ่นเก่า ไม่ใช้เพียงการซ่อน Sidebar เป็นหลักฐาน

## งานเสริมด้านสิทธิ์ การเข้ารหัส และกระบวนการ

### P2-1: ลดข้อมูลจาก API และตรวจย้อนหลังการเปิดดู/ส่งออก

เส้นทางเคสบางส่วนคืน `SELECT *` และข้อมูลที่ถอดรหัสเต็มด้วย [decryptCaseData.js](../../server/utils/decryptCaseData.js) ตัวแปลงนี้ยังส่งต่อ `identity_hash` หาก record มีฟิลด์นั้น; การ mask เฉพาะหน้าเว็บจึงไม่ใช่การลดข้อมูลฝั่ง API ส่วนประวัติ log ฝั่งผู้รับบริการ [patientRoutes.js:343](../../server/routes/patientRoutes.js#L343) ตรวจเจ้าของ response แล้ว แต่คืน `SELECT * FROM case_logs` ควรกำหนดว่า log/ข้อมูลเจ้าหน้าที่ใดผู้รับบริการดูได้

มี audit บางงานแก้ไข/เข้าสู่ระบบแล้ว แต่ยังไม่พบการบันทึกเปิดอ่านสุขภาพ เปิดข้อมูลเต็ม หรือส่งออกอย่างครอบคลุมในเส้นทางที่ตรวจ เมนูส่งออกใน [CaseDetailModal.jsx:1422](../../app/src/components/case/CaseDetailModal.jsx#L1422) ยังไม่ได้ผูก `cases.export` โดยตรง

แนะนำ DTO รายการเป็นข้อมูลขั้นต่ำ สิทธิ์แยกดูข้อมูลเต็ม/ดูสุขภาพ/ส่งออกตามหน่วยงานหรือเคส บันทึกผู้กระทำ หน่วยงาน เป้าหมาย เวลา ผลและเหตุผล โดยไม่คัดลอกสุขภาพ plaintext ลง audit การจำกัดปุ่มส่งออกไม่ป้องกันคนที่ได้รับข้อมูลเต็มจากการคัดลอก จึงต้องลดข้อมูลก่อนส่งและใช้กระบวนการควบคู่

### P2-2: กุญแจและข้อมูลที่ถอดรหัสไม่ได้

[encryption.js:17](../../server/utils/encryption.js#L17) ใช้ AES key กลางและ search key แยกจาก env ยังไม่มี key ID/rotation ใน ciphertext; `decrypt` คืนค่าเดิมเมื่อข้อมูลไม่ใช่ ciphertext หรือถอดรหัสล้มเหลวเพื่อรองรับ legacy

แนะนำเก็บกุญแจใน secret manager/KMS หรือกลไกที่แยกสิทธิ์จาก DB/backup ใช้ version/key ID รองรับหมุนและกู้คืนกุญแจ ตรวจ config ให้ fail เมื่อกุญแจผิด ก่อนเริ่มรับคำขอ สำหรับ ciphertext รุ่นใหม่ให้การยืนยันความถูกต้องล้มเหลวเป็น error ไม่คืนค่าเป็น plaintext; legacy reader ต้องระบุได้ชัดและมีแผนย้าย ข้อมูลค้นหาแบบ HMAC ควรแยกกุญแจจาก encryption และมีแผนหมุนด้วย

หลักวิศวกรรมอ้างอิง: [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html), [OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html)

### P2-3: Transport, session และเครื่องที่ใช้ร่วมกัน

[db.js:16](../../server/config/db.js#L16) สร้าง mysql2 pool โดยไม่มีตัวเลือก `ssl` จึงยังยืนยัน TLS จาก client configuration ไม่ได้ ต้องตรวจเครือข่าย/tunnel และ TLS จริงบน deployment หากต่อข้ามเครื่องให้ใช้ TLS พร้อมตรวจ CA/host ตาม [mysql2 SSL documentation](https://sidorares.github.io/node-mysql2/docs/documentation/ssl) รวม HTTPS, disk/backup encryption และบัญชี DB สิทธิ์ขั้นต่ำ

JWT/session ฝั่งเว็บยังอ่านได้จาก JavaScript ผ่าน sessionStorage/localStorage; JWT ลงลายเซ็นไม่ได้ซ่อน claims และ staff payload บางส่วนมีชื่อ แนะนำประเมิน HttpOnly+Secure+SameSite cookie และ CSRF ให้เข้ากับ flow, อายุ session, การถอน session, CSP และ MFA สำหรับผู้มีสิทธิ์สูง ตรวจการเปิด MFA บน Production จริง ไม่สรุปจาก .env ใน repo เพียงไฟล์เดียว

Draft ฟอร์มใน [FormView.jsx:80](../../app/src/pages/assessment/formView/FormView.jsx#L80) เก็บ answers/consents ใน sessionStorage มี TTL **4 ชั่วโมง** แต่ผูกแค่รหัสฟอร์ม ไม่ใช่บัญชี; [patientSession.js:33](../../app/src/utils/patientSession.js#L33) logout ลบ token/user ไม่ลบ draft ต้องป้องกันการคืนข้อมูลคนก่อนเมื่อเปลี่ยนผู้ใช้ในแท็บเดิม กำหนดการโอน guest draft ไปบัญชีที่เพิ่งเข้าสู่ระบบอย่างชัดเจน การใส่กุญแจเข้ารหัสไว้ใน JavaScript เดียวกันไม่ป้องกัน XSS

อ้างอิง: [OWASP HTML5 Security](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html), [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

### P2-4: ฐานกฎหมาย การส่งต่อ อายุเก็บ และสิทธิของเจ้าของข้อมูล

พบ `consent_given` สำหรับการผูกเลขบัตรใน flow ประเมิน แต่ boolean นี้อย่างเดียวไม่แสดงฐานกฎหมาย/วัตถุประสงค์/notice version/ผู้ให้ความยินยอม/เวลา/การถอน สำหรับทุกกิจกรรม ต้องตรวจเอกสารและกระบวนการนอกโค้ดเพิ่มเติม กำหนดฐานแยกการประเมิน รักษา จับคู่ประวัติ ส่งต่อ แจ้งเตือน และวิเคราะห์; หากใช้ consent กับเด็กต้องรองรับผู้ใช้อำนาจปกครองตามเงื่อนไข

ต้องมี privacy notice, บันทึกกิจกรรมและบทบาท controller/processor ของแต่ละองค์กร, ข้อตกลงบริการ/ส่งต่อ, retention แยกชนิดข้อมูลและสำรอง, ช่องทางขอสำเนา/แก้ไข/ลบ/ถอน และแผนเหตุละเมิด ไม่มีอายุเก็บสากลที่สรุปให้เวชระเบียนทุกชนิดได้จากโค้ด และไม่ควรลบข้อมูลที่มีหน้าที่ตามกฎหมายเก็บโดยอัตโนมัติเมื่อถอน consent

ข้อกฎหมายและแหล่งต้นทาง: [requirements.md](requirements.md) ข้อมูลสุขภาพเข้าข่ายมาตรา 26; ไม่จำเป็นต้องขอ consent ทุกกรณีหากเข้าเงื่อนไขข้อยกเว้นจริง มาตรการต้องเหมาะสมกับความเสี่ยง ไม่ได้สั่ง encrypt ทุกคอลัมน์ สิทธิ์เข้าถึงตามความจำเป็นและ audit trail เป็นส่วนหนึ่งของมาตรการขั้นต่ำตาม [ประกาศความมั่นคงปลอดภัย 2565](https://www.dol.go.th/media/813280155698073600/2026/01/hRdpKq9cQJsTw6f0b2yxYSZM.pdf)

## ลำดับดำเนินการและขอบเขตที่ยังต้องตรวจ

1. ปิดช่องตรวจสัมพันธ์ master/body และ API ที่หลุด scope; เปลี่ยน notification ให้ข้อมูลขั้นต่ำ; ออกแบบ invitation token ใหม่ก่อนขยายผู้ใช้จริง
2. ทำตัวเก็บข้อมูลสุขภาพแบบเข้ารหัสร่วมกัน พร้อม migration/backfill ที่อ่านกลับได้และ rollback; ตรวจทุก summary/answer/log/clinical/export ที่ซ้ำกัน
3. ลด DTO/แยกสิทธิ์เปิดข้อมูลเต็มและส่งออก พร้อม audit อ่าน/เปิดเผยข้ามองค์กร
4. ตรวจ deployment TLS, database/backup encryption, key management, MFA/session และ private file storage ด้วยหลักฐาน config/runtime ของระบบจริง
5. ยืนยันฐานกฎหมาย/notice/consent/retention/DSAR/DPO กับผู้รับผิดชอบแต่ละองค์กร และทดสอบการแจ้งเหตุ/กู้คืน

ยังไม่ได้ตรวจ production reverse proxy/TLS, backup/disk, secret manager, สมาชิกกลุ่ม Telegram จริง, ข้อตกลงผู้ให้บริการ, เอกสาร PDPA หรือทดสอบเจาะระบบ จึงไม่กล่าวว่าเกิดละเมิดแล้วหรือรับรองการปฏิบัติตามทั้งหมด มาตรฐานเว็บไซต์ กมช. 2568 เป็นข้อกำหนดอีกชุดที่มีผลแล้วสำหรับกลุ่มหน่วยงานที่อยู่ในขอบเขต ต้องตรวจสถานะผู้ดำเนินงานตามรายละเอียดใน requirements.md

การแก้ในรอบนี้จำกัดที่ตัวเลือกหน่วยงาน/การใช้ System Admin flag และ regression tests **ยังไม่ได้ migrate ข้อมูลสุขภาพ เปลี่ยน Telegram หรือเปลี่ยน token** จุด P1/P2 ข้างต้นเป็นงานที่เปิดอยู่

ผลตรวจโค้ดที่แก้: frontend unit 43 ผ่าน; backend 87 ผ่าน 1 ข้าม (integration ฐานข้อมูลส่งต่อไม่ได้เปิด flag); browser desktop/mobile 10 ผ่าน ครอบคลุมสามบทบาท ตัวเลือก all และสลับหน่วยงาน; production build ผ่าน มีคำเตือน bundle ใหญ่ตามเดิม
