# แผนแก้ไขความปลอดภัยและ PDPA — SuthieCare

วันที่จัดทำ: 3 ตุลาคม 2569

อ้างอิง [รายงานตรวจระบบ](D:/github-clone/suth-suthiecare/outputs/pdpa/security-audit.md) และ [ข้อกำหนด/แหล่งกฎหมายที่ตรวจไว้](D:/github-clone/suth-suthiecare/outputs/pdpa/requirements.md)

สถานะ: **แผนพร้อมใช้แบ่งงาน ยังไม่ได้เริ่มแก้โค้ดหรือย้ายข้อมูลตามแผนนี้** การเลือกหน่วยงานและ Sidebar ที่เสร็จแล้วเป็นฐานที่ต้องรักษา ไม่ถือว่าปิดข้อค้นพบ API/การเข้ารหัสในรายงาน

เป้าหมายคือป้องกันการเข้าถึงข้ามหน่วยงานและการเปิดเผยเกินจำเป็น เข้ารหัสข้อมูลสุขภาพอย่างสม่ำเสมอ รักษาข้อมูลเดิมและงานโรงพยาบาล/โรงเรียน/ส่งต่อให้ทำงานต่อได้ พร้อมมีหลักฐานการทดสอบและกระบวนการคุ้มครองข้อมูล

งานเอกสารและตรวจ Production เริ่มตั้งแต่ระยะ 0 ไม่รอให้เขียนโค้ดจบ งานที่มีความเสี่ยงสูงบน Production ต้องได้รับมาตรการชั่วคราวทันทีหลังยืนยันข้อเท็จจริง เช่น ปิด notification ที่มีข้อมูลเต็มหรือจำกัด endpoint ที่มีปัญหา โดยผู้ดูแล deployment

## สิ่งที่ต้องรักษาตามความต้องการระบบ

สิทธิ์ทำงานตรวจที่ API ตามสมาชิกหน่วยงานและงานที่อนุญาต การเป็น Admin ในหน่วยงานไม่ทำให้เป็น System Admin ระดับระบบ และการซ่อน Sidebar ไม่ถือเป็นการตรวจสิทธิ์ การเปิดดูข้อมูลสุขภาพเต็มของ System Admin ต้องตรวจย้อนหลังได้เช่นเดียวกับบทบาทอื่น โดยยังรักษาขอบเขตเห็นทุกหน่วยงานตามคำขอ

ฟอร์มสาธารณะยังรองรับไม่ Login ตาม publish settings การเปิดฟอร์มสาธารณะไม่ให้สิทธิ์อ่านประวัติ/ข้อมูลผู้รับบริการ ไม่ใช้ชื่อ-นามสกุลหรือเลขบัตรอย่างเดียวเป็นหลักฐานยืนยันตัวตนเพื่อเปิดประวัติ การส่งต่อยังเปิดเพียงข้อมูลสรุปที่กำหนดและสถานะร่วมกัน ไม่เปิดคำตอบ/คลินิกเชิงลึกของต้นทางโดยอัตโนมัติ

## ระยะ 0: เตรียมข้อมูลและฐานทดสอบ

### PDPA-00 — สำรวจเส้นทางข้อมูลและเตรียมการกู้คืน

เจ้าของงาน: นักพัฒนา + ผู้ดูแลฐานข้อมูล/ระบบ; ผู้รับผิดชอบ PDPA ช่วยจัดประเภทข้อมูล

งาน:

- ทำ inventory ตาราง/คอลัมน์ ชนิด SQL, ฟิลด์ JSON, สำเนา summary/raw_answers, log, referral, ไฟล์แนบ, export, browser storage และผู้รับข้อมูลภายนอก แยกข้อมูลระบุตัว สุขภาพ ข้อมูลอ้างอิงและข้อมูลที่เผยแพร่ได้
- ทำรายการ API อ่าน/เขียนและเส้นทางแก้ไข/alias ที่ต้องใช้ organization scope รวม cache และ background job ระบุช่องที่มี plaintext/ciphertext ผสมโดยไม่พิมพ์ค่าจริง
- ใช้ข้อมูลจำลองเป็นชุดหลักในการทดสอบ หากต้องใช้ข้อมูลจริงเพื่อทวน migration ให้จำกัดสิทธิ์และพื้นที่แยกที่ได้รับอนุญาต ไม่คัดลอก Production ลงเครื่องพัฒนาโดยปริยาย
- เตรียม staging, snapshot ที่ป้องกันแล้ว, key recovery และทดสอบ restore เก็บ baseline จำนวนรายการ/ความสัมพันธ์/ชนิดข้อมูล; บันทึก schema และเวอร์ชันแอปที่อ่านข้อมูลปัจจุบันได้
- เปิดทะเบียนงานตาม ID ในแผน ระบุผู้รับผิดชอบ สถานะ หลักฐาน และข้อค้นพบเดิมที่ต้องปิด

เกณฑ์ผ่าน: มี data map/API map, ชุดทดสอบหน่วยงาน A/B, แผนสำรองและผล restore ทดสอบ รวมรายการตัดสินใจค้าง ไม่ต้องรอเอกสารองค์กรครบเพื่อเริ่ม PDPA-01/02

## ระยะ 1: ปิดช่องเร่งด่วน

### PDPA-01 — ตรวจสัมพันธ์เคสและสิทธิ์เขียนให้ครบ

เชื่อมรายงาน: P1-4 ข้อ 1 | เจ้าของงาน: Backend | พึ่งพา: PDPA-00

ไฟล์หลัก: [caseRoutes.js](D:/github-clone/suth-suthiecare/server/routes/caseRoutes.js), [authorization.js](D:/github-clone/suth-suthiecare/server/authorization/authorization.js)

งาน:

- POST `/cases/:id/logs` ต้องโหลด response ที่ตรวจหน่วยงานแล้ว และ derive master case จากความสัมพันธ์ในฐานข้อมูล ถ้า client ส่ง master ID ที่ไม่ตรงให้ปฏิเสธ ไม่มีการเชื่อ body/query เพื่อเลือก owner อีกตัว
- ตรวจ master, staff ที่รับผิดชอบ, status, service และ appointment ตามความสัมพันธ์และสิทธิ์; actor ใน audit ใช้ผู้ใช้ที่ยืนยันตัวตน ไม่เชื่อชื่อ/ID ผู้กระทำจาก body
- ครอบ log + status/risk update ด้วย transaction ให้บันทึกครบหรือ rollback ทั้งชุด
- ตรวจเส้นทาง `target=master`, alias และ System Admin ในบริบท `all`; งานสร้าง/แก้ต้องระบุหน่วยงานปลายทางที่แน่นอน ไม่ให้ `all` กลายเป็น owner ของข้อมูล

เกณฑ์ผ่าน: ผู้ใช้ A มีสิทธิ์เขียน A แต่ส่ง master/staff/status ของ B แล้วไม่ได้แก้ข้อมูล B; response/master ผิดสัมพันธ์ถูกปฏิเสธแม้อยู่หน่วยงานเดียวกัน; rollback ได้เมื่อเขียนขั้นใดล้มเหลว; งานปกติของ A ยังทำได้

### PDPA-02 — แจ้งเตือนด้วยข้อมูลขั้นต่ำ

เชื่อมรายงาน: P1-1 | เจ้าของงาน: Backend + ผู้ดูแล notification | พึ่งพา: PDPA-00

ไฟล์หลัก: [formRoutes.js](D:/github-clone/suth-suthiecare/server/routes/formRoutes.js), [telegram.js](D:/github-clone/suth-suthiecare/server/utils/telegram.js)

งาน:

- เปลี่ยนข้อความเป็น “มีรายการใหม่” พร้อมรหัสอ้างอิงและลิงก์ที่ต้องตรวจสิทธิ์ งดชื่อ เบอร์ เลขบัตร ผลคะแนน ความเสี่ยง และชื่อฟอร์ม/คลินิกที่เผยภาวะสุขภาพ
- สำหรับงานหน่วยงาน ให้ resolve ปลายทางที่อนุญาตจาก organization ID ฝั่ง server ถ้าไม่มีปลายทางให้ข้าม notification และแจ้งปัญหาการตั้งค่าในระบบ ไม่ fallback ไปกลุ่มกลางที่มีผู้รับต่างหน่วยงาน
- log ผลส่งเฉพาะ metadata และ error ที่ตัด token/PII แล้ว ไม่มีการใส่ข้อมูลผู้รับบริการใน URL
- ให้ผู้รับผิดชอบตรวจสมาชิกกลุ่มจริงและฐานการส่งออกไปผู้ให้บริการ หากยังยืนยันไม่ได้ให้ปิด external notification ของหน่วยงานนั้นได้ โดยยังบันทึกเคสในระบบตามปกติ

เกณฑ์ผ่าน: ทดสอบ sender จำลอง ไม่ส่งออกจริง; ไม่มี PII/สุขภาพในข้อความ URL หรือ error log; A ไม่ไปปลายทาง B; ไม่มีปลายทางแล้วไม่ส่งไปกลุ่มกลาง; ผู้ไม่มีสิทธิ์เปิดลิงก์ไม่ได้

### PDPA-03 — แยก token สำหรับเชิญทำฟอร์มออกจากข้อมูลฐานข้อมูล

เชื่อมรายงาน: P1-3 | เจ้าของงาน: Backend + Frontend | พึ่งพา: PDPA-01

ไฟล์หลัก: [caseRoutes.js](D:/github-clone/suth-suthiecare/server/routes/caseRoutes.js), [api.js](D:/github-clone/suth-suthiecare/app/src/services/api.js), [FormView.jsx](D:/github-clone/suth-suthiecare/app/src/pages/assessment/formView/FormView.jsx)

งาน:

- สร้าง invitation token แบบสุ่มด้วยแหล่งสุ่มสำหรับงานเข้ารหัส เก็บเฉพาะ hash พร้อมหน่วยงาน ฟอร์ม ผู้รับ/เคส purpose, expiry, revoked_at และสถานะการใช้
- ตรวจสิทธิ์และความสัมพันธ์ตอนสร้างและตอนใช้ token ปิด API `/decode-token` ที่รับ ciphertext ทั่วไป ไม่ย้ายปัญหาไป endpoint ชื่อใหม่
- กำหนดอายุใช้จากความเสี่ยง/flow และ config ทดสอบ; ใช้ rate limit และ audit การออก/ใช้/เพิกถอนโดยไม่ log token ดิบ
- ลิงก์สำหรับ public form เปิดเนื้อหาแบบฟอร์มได้ตาม publish settings แต่ห้ามส่ง PII/ประวัติโดยอาศัย token อย่างเดียว หากต้องผูกผู้รับหรือเติมข้อมูลส่วนบุคคล ให้มีการยืนยันผู้รับตาม flow ที่ออกแบบไว้
- หากกำหนดใช้ครั้งเดียว ให้ใช้ตอนส่งข้อมูลสำเร็จใน transaction ไม่ใช้ตอนเปิดหน้า GET เพื่อไม่ให้ตัวสแกนลิงก์ทำ token หมดสิทธิ์ก่อนผู้รับใช้
- ยุติการใช้ลิงก์เก่าที่บรรจุเลขบัตรหรือ AES ciphertext พร้อมวิธีออกลิงก์ใหม่ที่จำเป็น ไม่เปิด generic decrypt กลับเพื่อรองรับลิงก์เก่า

เกณฑ์ผ่าน: token หมดอายุ/เพิกถอน/ผิดฟอร์ม/ผิดหน่วยงาน/ผิดผู้รับถูกปฏิเสธ; ciphertext ของ DB ใช้แทน token ไม่ได้; ทดลองใช้พร้อมกันไม่เกินจำนวนครั้งที่อนุญาต; public form แบบไม่มี invitation ยังทำงานตามเดิม

### PDPA-04 — กำหนดขอบเขตข้อมูลอ้างอิงและปิด API รุ่นเดิมที่หลุด scope

เชื่อมรายงาน: P1-4 ข้อ 2 | เจ้าของงาน: Backend + ผู้ดูแลข้อมูลหน่วยงาน | พึ่งพา: PDPA-00/01

ไฟล์หลัก: [requestScope.js](D:/github-clone/suth-suthiecare/server/authorization/requestScope.js), [index.js](D:/github-clone/suth-suthiecare/server/index.js), [staffRoutes.js](D:/github-clone/suth-suthiecare/server/routes/staffRoutes.js), [caseRoutes.js](D:/github-clone/suth-suthiecare/server/routes/caseRoutes.js)

แนวทางเริ่มต้น: รายชื่อผู้รับผิดชอบและ template ที่หน่วยงานสร้างใช้ scope หน่วยงาน; ค่ามาตรฐานกลางที่ตั้งใจแชร์ให้ระบุชัดว่า shared และ System Admin เป็นผู้แก้ ห้ามถือว่า `organization_id = NULL` เป็นข้อมูลที่ทุกคนแก้ได้โดยปริยาย

งาน:

- ครอบคลุม `/staffs`, `/services`, `/templates`, `/case-statuses`, `/status-options` ทั้งอ่าน/สร้าง/แก้/ลบ/alias ตรวจ permission และ scope ที่ middleware และ SQL
- เพิ่ม owner/scope ที่จำเป็นและทำ mapping ข้อมูลเก่า: อ้างอิงความสัมพันธ์ที่พิสูจน์ได้; รายการที่ระบุเจ้าของไม่ได้ให้อยู่สถานะรอตรวจ ไม่เปิดเป็นของทุกหน่วยงาน
- แยก cache ด้วย scope/หน่วยงานและชนิดข้อมูล; invalidate เฉพาะขอบเขตที่ถูกแก้; ไม่ใช้ global cache ของ A ตอบ B
- ตรวจผู้รับผิดชอบและ reference ที่ client เลือกอีกครั้งฝั่ง server ไม่ใช้ dropdown ที่กรองแล้วเป็นหลักฐานสิทธิ์

เกณฑ์ผ่าน: read/write/cache ไม่ข้าม A/B; หน่วยงานแก้ shared definition ไม่ได้; System Admin จัดการ shared ได้ตาม policy; orphan/legacy reference ไม่เผยแพร่โดยอัตโนมัติ; old aliases ใช้กฎเดียวกัน

เกณฑ์จบระยะ 1: ปิดข้อ P1-1, P1-3 และ P1-4 ด้วยหลักฐาน regression และ staging ไม่ถือว่าปิด P1-2 จนกว่าจะผ่านระยะ 2

## ระยะ 2: เข้ารหัสและย้ายข้อมูลโดยรักษาการอ่านเดิม

### PDPA-05 — ตัวเก็บ/อ่านข้อมูลเข้ารหัสที่มีเวอร์ชันและจัดการกุญแจได้

เชื่อมรายงาน: P1-2, P2-2 | เจ้าของงาน: Backend + ผู้ดูแล secrets | พึ่งพา: PDPA-00

ไฟล์หลัก: [encryption.js](D:/github-clone/suth-suthiecare/server/utils/encryption.js), [storedAnswer.js](D:/github-clone/suth-suthiecare/server/utils/storedAnswer.js), [decryptCaseData.js](D:/github-clone/suth-suthiecare/server/utils/decryptCaseData.js)

งาน:

- ออกแบบ API เก็บ/อ่าน JSON ที่รักษาชนิด null, 0, false, string, array และ object ใช้ authenticated encryption เช่น AES-GCM และ IV ใหม่ทุกครั้ง
- ciphertext ใหม่มี marker/version/key ID และข้อมูลที่จำเป็นสำหรับตรวจความถูกต้อง; สำหรับคอลัมน์ JSON ต้องเก็บ envelope ที่เป็น JSON ถูกต้อง ตรวจชนิดคอลัมน์ก่อนเลือกโครงสร้าง
- พิจารณาผูก authenticated context กับหน่วยงาน/ชนิดฟิลด์/record เพื่อป้องกันการนำ ciphertext ไปสลับข้ามขอบเขต โดยออกแบบตอนยังไม่มี record ID ให้แน่นอน
- แยก key ตาม purpose: field encryption, identity search, session signing; invitation ใช้ random token hash ไม่ใช้ AES ของ DB; กำหนด active key และ read key รุ่นก่อน พร้อมแผนหมุน/กู้คืน
- config key ผิดทำให้ระบบไม่พร้อมรับคำขอ; ciphertext ใหม่ผิด tag/key/context ต้อง error ไม่คืนค่าเดิมแบบ plaintext แยก legacy reader ที่ระบุรูปแบบและมีวันยุติได้
- กุญแจไม่อยู่ใน repository, API response, audit หรือ backup ชุดเดียวกับข้อมูลโดยไม่แยกสิทธิ์

เกณฑ์ผ่าน: round-trip ครบทุกชนิด; tamper/wrong key/wrong context ถูกปฏิเสธ; หมุน key แล้วอ่านข้อมูลเก่าได้; missing key ไม่เริ่มบริการที่เขียนข้อมูล; legacy ไม่ถูกเข้าใจผิดหรือเข้ารหัสซ้ำ

### PDPA-06 — ใช้ตัวเก็บร่วมกันกับข้อมูลสุขภาพทุกเส้นทาง

เชื่อมรายงาน: P1-2 | เจ้าของงาน: Backend + Frontend ที่อ่านผล | พึ่งพา: PDPA-05 และแผนข้อมูล PDPA-00

งาน:

- classification ตัดสินจาก schema ฟอร์มที่ server โหลด ไม่อาศัยชื่อคำถามที่ client ส่ง ครอบคลุมสุขภาพและ PII ใน insert/edit/read รวมฟอร์มเก่าและคำถามย่อย
- เข้ารหัสคำตอบและข้อมูลสุขภาพที่ซ้ำใน summary/raw_answers/main_issue/คะแนน รวม `clinical_data`, `case_logs.detail/staff`, `appointments.note`; ตรวจตารางอื่นจาก inventory เพิ่มด้วย
- แยกข้อมูลที่ใช้รายงานอย่างจำเป็น เช่น วันเวลา/สถานะงาน จากรายละเอียดสุขภาพ ระบุว่าคะแนน/ความเสี่ยงที่ผูกคนเป็นข้อมูลสุขภาพและต้องป้องกัน ไม่ตั้งข้อยกเว้นเพียงเพราะเป็นตัวเลข
- ข้อมูลกายภาพนักเรียนออกแบบการอ่าน/วิเคราะห์ที่ได้รับสิทธิ์: ใช้ฟิลด์เข้ารหัสหรือแยกพื้นที่และสิทธิ์ตามภัยคุกคาม พร้อม disk/database encryption โดยบันทึกเหตุผลของข้อมูลที่ยังต้อง query เป็นตัวเลข
- อีเมลและตัวระบุที่ต้องค้นหาให้ประเมิน encrypt + keyed lookup แยก migration จากสุขภาพหากกระทบ login/OTP มาก; รหัสผ่านยังใช้ password hashing
- ตรวจ reader ของประวัติผู้รับบริการ หน้ารายการ/รายละเอียด โรงเรียน รายงาน ส่งต่อและ export ทั้งหมด ไม่เข้ารหัสเฉพาะ API สร้างแล้วปล่อย API แก้เขียน plaintext

เกณฑ์ผ่าน: create/edit/read/export ตรงกันทุกชนิด; schema ภาษาไทย/อังกฤษ/ไม่มี keyword ได้ผลเหมือนกัน; ข้อมูลใหม่ไม่ซ้ำ plaintext ใน summary/log อีกชุด; การส่งต่อยังไม่เผยรายละเอียดต้นทาง และรายงานที่อนุญาตยังทำงานได้

### PDPA-07 — Migration/backfill ที่ตรวจรับและหยุด/ทำต่อได้

เชื่อมรายงาน: P1-2, P2-2 | เจ้าของงาน: Backend + DBA | พึ่งพา: PDPA-05/06; ตรวจ restore ผ่านก่อน

ลำดับนำใช้:

1. เพิ่ม schema แบบรองรับข้อมูลเก่า และ deploy reader ที่อ่านทั้ง legacy กับ envelope ใหม่ได้ก่อนเปิด writer ใหม่
2. ทดสอบใน staging เปิด writer ใหม่และทวนว่าทุก reader ใช้ได้ บล็อก app รุ่นเก่าที่อ่านรูปแบบใหม่ไม่ได้ ไม่ dual-write ข้อมูลสุขภาพ plaintext เพิ่ม
3. dry-run แสดงจำนวน/ประเภท/รายการผิดปกติโดยไม่แสดงค่า; migrate เป็น batch มี checkpoint และทำซ้ำได้ ใช้ lock หรือ version check ไม่ทับข้อมูลที่ผู้ใช้เพิ่งแก้
4. หลังแต่ละ batch ตรวจจำนวน ความสัมพันธ์ และอ่านกลับเทียบชนิด/ค่าในกระบวนการที่จำกัดสิทธิ์ ไม่สร้างรายงาน plaintext ถาวร
5. รายการถอด legacy ไม่ได้/เจ้าของไม่ชัดให้หยุดหรือแยกตรวจ ห้ามเดา ห้ามลบทิ้ง และห้าม mark ว่าสำเร็จ
6. เมื่อยืนยันครบแล้ว เลิก reader fallback แบบกำกวม และจัดการสำเนา plaintext เก่า/snapshot ตามนโยบายอายุเก็บและความจำเป็น

Rollback: กลับได้เฉพาะ release ที่อ่าน envelope ใหม่ได้; การ revert ไปแอปเดิมอาจอ่านข้อมูลไม่ได้ หาก writer/migration มีปัญหาให้หยุด backfill/ปิด writer ที่มีปัญหาและใช้ maintenance/read-only ตามแผน เก็บกุญแจรุ่นก่อนตลอดช่วงกู้คืน Restore ต้องรองรับข้อมูลที่มีการแก้หลัง snapshot ไม่ทับข้อมูลใหม่ทั้งฐานโดยไม่มีการ reconcile

เกณฑ์ผ่าน: ซ้อม migration และ rollback/restore ใน staging; จำนวนและความสัมพันธ์ตรง baseline หลังหักรายการใหม่ที่ตรวจได้; ไม่มีรายการไม่ทราบสถานะ; key รุ่นเก่า/ใหม่และ backup อ่านได้เฉพาะผู้มีสิทธิ์

## ระยะ 3: ลดการเปิดเผยและตรวจการเข้าถึง

### PDPA-08 — DTO ข้อมูลขั้นต่ำและสิทธิ์เปิดเต็ม/ส่งออก

เชื่อมรายงาน: P2-1 | เจ้าของงาน: Backend + Frontend + ผู้รับผิดชอบหน่วยงาน | พึ่งพา: PDPA-01/04/06

งาน:

- กำหนด allowlist ของแต่ละ API แยกรายการ/รายละเอียด/ข้อมูลผู้รับบริการ ไม่ส่ง identity_hash, token, internal IDs ที่ไม่จำเป็น หรือ plaintext เต็มไป mask ที่ client
- รายการแสดงข้อมูลขั้นต่ำ; เปิด PII เต็ม/ข้อมูลคลินิก/ส่งออกด้วยสิทธิ์หน่วยงานที่ออกแบบแยก เช่น `pii.view`, `clinical.view` และใช้ `cases.export` ที่มีอยู่ให้ครบ ไม่เพิ่มสิทธิ์เต็มให้ทุก role อัตโนมัติ
- กำหนด log ที่ผู้รับบริการดูได้: เปิดเฉพาะ patient-visible note ไม่เปิด internal staff note หรือข้อมูลบุคคลที่สามทั้งหมดด้วย SELECT *
- ตรวจ permission ของ export ฝั่ง server หาก export ฝั่ง client ให้ส่งเฉพาะ DTO ที่ role ได้รับและซ่อน/ปฏิเสธ action ตามสิทธิ์ การซ่อนปุ่มไม่สามารถป้องกันการคัดลอกข้อมูลที่ browser ได้รับแล้ว
- ส่งต่อใช้ DTO สรุปเดิม ตรวจรายการ/อ่าน/อัปเดตโดยต้นทาง-ปลายทางตามสถานะ ไม่เพิ่มสิทธิ์เข้าถึงแบบฟอร์มต้นทางจากการรับส่งต่อ

เกณฑ์ผ่าน: role ไม่มี reveal ได้เฉพาะ masked DTO; ไม่มี export ได้รับการปฏิเสธตาม endpoint/action; staff Sidebar ยังมีเฉพาะผู้มารับบริการ; ผู้รับบริการเห็นเฉพาะข้อมูลที่ควรเปิด; referral projection ไม่มีสุขภาพเชิงลึก

### PDPA-09 — Audit การอ่าน เปิดเผย ส่งออกและสิทธิ์สูง

เชื่อมรายงาน: P2-1, P2-2 | เจ้าของงาน: Backend + ผู้ดูแลระบบ | พึ่งพา: PDPA-08

งาน:

- บันทึก actor, organization, target, action, เวลา, request ID, ผล, เหตุผลเมื่อจำเป็น สำหรับเปิดข้อมูลเต็ม/คลินิก/ประวัติข้ามหน่วยงาน ส่งออก ส่งต่อ เปลี่ยนสิทธิ์และการใช้สิทธิ์ System Admin
- ใช้ event metadata ไม่คัดลอกคำตอบ ชื่อ เลขบัตร notes token หรือ key ลง audit; จำกัดคนอ่าน audit และป้องกันการแก้ย้อนหลัง/กำหนดอายุเก็บ
- ระบุพฤติกรรมเมื่อ audit ใช้ไม่ได้: action เปิดเผย/ส่งออกที่กำหนดว่าต้องมีหลักฐานต้องถูกระงับหรือบันทึกใน durable queue ก่อนสำเร็จ ไม่แค่ console.warn แล้วให้ผ่าน
- ตรวจ alert จากพฤติกรรมที่กำหนด เช่น ดาวน์โหลดมาก/ข้ามหน่วยงานผิดปกติ โดยไม่ส่งรายละเอียดสุขภาพไปช่องทางแจ้งเตือน

เกณฑ์ผ่าน: ตอบได้ว่าใครเปิด/ส่งข้อมูลใดจากหน่วยงานใดเมื่อไร; log ไม่มี PII/สุขภาพดิบ; audit failure ได้พฤติกรรมตาม policy; role ทั่วไปแก้/ลบ audit ไม่ได้

### PDPA-10 — Session, MFA และ draft บนเครื่องที่ใช้ร่วมกัน

เชื่อมรายงาน: P2-3 | เจ้าของงาน: Backend + Frontend + ผู้ดูแล authentication | พึ่งพา: PDPA-00; ทำงานระหว่างระยะ 2 ได้

งาน:

- แก้ draft ผูกกับบัญชี/guest flow, TTL และ logout/เปลี่ยนบัญชีเคลียร์ข้อมูล; การรับ guest draft หลัง login ต้องเป็น flow ที่ชัดเจน ไม่คืน draft ของ A ให้ B จากรหัสฟอร์มเดียวกัน
- ออกแบบ session ที่ใช้ HttpOnly/Secure cookie พร้อม SameSite และ CSRF ตาม origins จริง ตรวจ HTTPS reverse proxy, CORS, refresh/logout/revocation และ login redirect ก่อนเลิก browser token storage
- ลด claims ที่มี PII, กำหนด idle/absolute timeout และยืนยันตัวตนซ้ำสำหรับงานเสี่ยงตาม policy
- เปิด/บังคับ MFA สำหรับผู้มีสิทธิ์สูงตามนโยบายที่ตกลง พร้อม enrollment, recovery และกรณีถอนสิทธิ์; ตรวจการตั้งค่าที่ใช้จริงบน deployment
- ทวน CSP/XSS และหน้าที่แสดง rich text โดยไม่ทำให้ flow ปัจจุบันเสีย

เกณฑ์ผ่าน: A logout แล้ว B ในแท็บเดิมไม่เห็น draft/ประวัติ A; cookie flags และ CSRF ตรวจได้; logout/revoke ใช้ token เก่าต่อไม่ได้ตาม session policy; MFA/recovery/timeout ทำงาน; guest form ยังใช้ได้

### PDPA-11 — ตรวจ Production, กุญแจ สำรองและไฟล์

เชื่อมรายงาน: P2-2/3 | เจ้าของงาน: DevOps/DBA | เริ่มหลัง PDPA-00; ต้องผ่านก่อน release

งาน:

- ตรวจและเก็บหลักฐาน HTTPS, reverse proxy, MySQL TLS/CA/host verification สำหรับการเชื่อมต่อที่ต้องป้องกัน, DB network/firewall และบัญชี application สิทธิ์ขั้นต่ำ
- ยืนยัน database/disk/backup encryption และแยกสิทธิ์ของ keys/secrets; ทดสอบกู้คืนทั้งข้อมูลและ key ไม่ยืนยันจาก .env ใน repo อย่างเดียว
- ตรวจไฟล์แนบ/รายงาน export/URL ดาวน์โหลด: private storage, organization/record permission ก่อนอ่าน, อายุลิงก์, อายุเก็บ, cache และ log ที่ไม่เผยข้อมูล
- สแกน repository และ logs เพื่อหาการหลุด secret ด้วยผลแบบไม่พิมพ์ค่า; ถ้าพบให้หมุน/เพิกถอนตามประเภทพร้อมตรวจการใช้งาน ไม่ถือว่าลบไฟล์แล้ว secret ปลอดภัย
- ตรวจ scope มาตรฐานเว็บไซต์สำหรับผู้ดำเนินงานจริงตาม requirements.md แล้วเติมข้อกำหนดที่ใช้กับ deployment นี้

เกณฑ์ผ่าน: มีหลักฐาน runtime/config ที่ตัด secret แล้ว; TLS ตรวจ certificate จริง ไม่ใช้การปิด verification เป็นทางแก้; บุคคลภายนอกเปิดไฟล์ส่วนตัวไม่ได้; restore และ key recovery ผ่าน; ระบุสิ่งที่ยังตรวจไม่ได้พร้อมเจ้าของและวันดำเนินการ

## งานองค์กรที่ทำควบคู่

### PDPA-12 — ฐานกฎหมาย Notice, retention, สิทธิและเหตุละเมิด

เชื่อมรายงาน: P2-4 | เจ้าของงาน: ผู้รับผิดชอบ PDPA/กฎหมาย + โรงพยาบาล/โรงเรียน + ผู้ดูแลระบบ | เริ่มระยะ 0

งาน:

- ทำ purpose register แยกประเมิน รักษา จับคู่ประวัติ ส่งต่อ แจ้งเตือน วิเคราะห์ และระบุข้อมูล/ผู้รับ/ฐานที่ใช้จริง; กำหนด controller/processor และข้อตกลงหน่วยงาน/ผู้ให้บริการ
- ทบทวน privacy notice ให้ตรงข้อมูลและผู้รับจริง ถ้ากิจกรรมใช้ consent ให้เก็บ purpose, notice version, ผู้ให้/ผู้แทน, เวลา/ช่องทาง และการถอนตาม flow; ไม่ใช้ consent ผูกเลขบัตรแทนความยินยอมทุกกิจกรรม และไม่บังคับ consent ที่ไม่จำเป็นเพื่อรับบริการ
- รองรับกรณีเด็ก/ผู้แทนเมื่อใช้ฐาน consent ตามเงื่อนไขที่ผู้รับผิดชอบยืนยัน; ประเมินหน้าที่ DPO และมาตรฐานอื่นตามสถานะองค์กรจริง
- กำหนด retention แยกเวชระเบียน/แบบประเมิน/ส่งต่อ/บัญชี/OTP/audit/export/backup และ legal hold; สร้าง job/รายงานลบหรือทำให้ไม่ระบุตัวเมื่อครบเกณฑ์ มี dry-run และตรวจผล
- ตั้งกระบวนการรับคำขอเจ้าของข้อมูล ยืนยันตัวตน ตรวจขอบเขต/ข้อยกเว้น ส่งข้อมูลอย่างปลอดภัย และบันทึกผล ครอบคลุมข้อมูลที่ส่งต่อ/สำเนา ไม่สร้าง admin API ที่ปลดล็อกข้อมูลทั้งหมดโดยไม่มีตรวจสิทธิ์
- ทำ incident runbook: ผู้รับแจ้ง การกักกัน เก็บหลักฐาน ประเมินความเสี่ยง การตัดสินใจแจ้งและผู้รับผิดชอบเวลา ใช้ข้อกำหนดการแจ้งเหตุที่ตรวจไว้ใน requirements.md และซ้อมสถานการณ์ก่อนใช้งาน
- หากยืนยันว่ามีการเปิดเผยโดยมิชอบอยู่แล้ว ให้เริ่ม incident runbook ทันที ไม่รอจบโครงการแก้ไข

เกณฑ์ผ่าน: ได้ policy ที่องค์กรรับรองและนำไปใช้ได้จริงพร้อมคนรับผิดชอบ; ทดลองรับคำขอ/ถอน consent/retention job และซ้อมเหตุละเมิดได้ ไม่กำหนดอายุเก็บหรือฐานกฎหมายสากลจากชื่อระบบเพียงอย่างเดียว

รายการตัดสินใจที่ต้องมีผู้รับผิดชอบให้ข้อเท็จจริงระหว่างทำงาน:

| เรื่อง                                | แนวทางเริ่มต้นในแผน                                                | ผู้ยืนยัน                                |
| ------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------- |
| ข้อมูลอ้างอิงกลางหรือรายหน่วยงาน      | shared มาตรฐานแก้โดย System Admin; custom/รายชื่อ scoped           | เจ้าของระบบ + หน่วยงาน                   |
| invitation อายุ/ผู้รับ/จำนวนครั้ง     | อายุจำกัด ผูก purpose/form/org; ไม่เปิด PII ด้วย bearer อย่างเดียว | เจ้าของ flow + ผู้รับผิดชอบ PDPA         |
| ฟิลด์ตัวเลขที่จำเป็นต่อ analytics     | ต้องมีเหตุผลจำเป็นและมาตรการป้องกัน ไม่ยกเว้นเพราะเป็นตัวเลข       | ทีมรายงาน + DBA + ผู้รับผิดชอบ PDPA      |
| ปลายทาง Telegram และบทบาทผู้ให้บริการ | ไม่มีปลายทางที่ตรวจแล้วไม่ fallback ไปกลุ่มกลาง                    | ผู้ดูแล notification + ผู้รับผิดชอบ PDPA |
| ฐานการประมวลผล/ส่งต่อ อายุเก็บและ DPO | ยืนยันจากภารกิจ สัญญา กฎหมายเฉพาะ และองค์กรจริง                    | ผู้รับผิดชอบ PDPA/กฎหมาย                 |
| origins, secrets, backup และ TLS จริง | ตรวจบน staging/Production ด้วยหลักฐาน ไม่เดาจาก repo               | DevOps/DBA                               |

รายการเหล่านี้ไม่ขัดขวางการแก้ PDPA-01/02 และการสร้างชุดทดสอบด้วยข้อมูลจำลอง แต่ต้องปิดก่อน deploy ส่วนที่พึ่งข้อเท็จจริงนั้น

## ระยะ 4: ตรวจรับและปล่อยใช้งาน

### PDPA-13 — Security regression, migration rehearsal และ release

เจ้าของงาน: นักพัฒนา + ผู้ทดสอบ + DBA/DevOps + ผู้รับผิดชอบองค์กร | พึ่งพา: งานที่เกี่ยวข้องทั้งหมดข้างต้น

ชุดตรวจขั้นต่ำ:

| กลุ่ม              | สิ่งที่ต้องพิสูจน์                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| บทบาท/หน่วยงาน     | System Admin all ได้; Admin/Staff all/B ไม่ได้; unit Admin ไม่ยกระดับระบบ; scope ครบทั้ง path/body/query/cache/alias                       |
| เคส/ส่งต่อ         | ปลอม master/foreign key ไม่ได้; tx rollback; ต้นทาง/ปลายทางเห็นเฉพาะสรุป; concurrent update และ version ยังถูกต้อง                         |
| Encryption         | insert/edit/read/export ทุกชนิด; tamper/wrong key/context fail; ไม่มี health plaintext ซ้ำ; backfill/resume/rotation/restore ไม่เสียข้อมูล |
| Token/notification | ciphertext DB ถอดผ่าน invite ไม่ได้; expiry/revoke/replay ตาม policy; notification/log ไม่มี PII และส่งถูกหน่วยงาน                         |
| PII/audit          | DTO รายการลดข้อมูล; reveal/export ใช้สิทธิ์; patient-visible notes เท่านั้น; audit failure และการเปิดข้ามหน่วยงานตรวจย้อนหลังได้           |
| Session/draft      | MFA/timeout/revoke/CSRF/cookie flags; เปลี่ยนบัญชีไม่คืนข้อมูลคนก่อน; guest/login form ยังทำงาน                                            |
| Infra/กระบวนการ    | TLS/private file/backup key recovery ผ่าน; incident drill/DSAR/retention ทดลองได้; เอกสารและผู้รับผิดชอบครบ                                |

ใช้ unit/integration tests สำหรับสิทธิ์ transaction และ encryption; ใช้ browser tests สำหรับ desktop/mobile และ flow จริง; ใช้ staging DB สำหรับ migration/concurrency; การตรวจ Production ใช้หลักฐานที่ได้รับอนุญาต ไม่ทดสอบด้วยการส่งข้อมูลผู้รับบริการออกไปยัง Telegram

แนะนำแบ่งการส่งมอบเป็นชุดตรวจสอบได้:

1. เคส ownership/transaction และ scoped references (PDPA-01/04)
2. Notification ขั้นต่ำและปลายทาง (PDPA-02)
3. Invitation token และหน้าใช้งาน (PDPA-03)
4. Encryption codec/key lifecycle พร้อม schema/reader ที่รองรับ (PDPA-05)
5. Writer/reader สุขภาพและ migration tools (PDPA-06/07; deploy ตามลำดับ reader → writer → backfill)
6. DTO/สิทธิ์/audit (PDPA-08/09)
7. Session/draft และหลักฐาน infra/process (PDPA-10–13)

ไม่จำเป็นต้องรอทุกชุดเพื่อส่ง patch เร่งด่วนที่ทดสอบครบ แต่ห้ามระบุว่า “ปิดรายงาน PDPA แล้ว” ขณะ P1 หรือเงื่อนไขสำคัญยังค้าง การขยายหลายหน่วยงาน/ข้อมูลสุขภาพจริงต้องตรวจ release gates ด้านล่าง

Release gates:

- ปิด P1 ทั้ง 4 ข้อพร้อมหลักฐานทดสอบและรายการ API ที่ครอบคลุม ไม่มีเพียง screenshot เมนู
- Production มี reader รองรับรูปแบบใหม่ก่อน writer/backfill และมี rollback ที่ไม่ทำข้อมูลใหม่หาย
- สิทธิ์เปิดเผย/export/audit, session/MFA ที่กำหนด, TLS/secrets/private storage/backup restore ผ่าน; ถ้ามี P2 ที่เลื่อน ต้องบันทึกเหตุผล มาตรการชดเชย เจ้าของและวันแก้ โดยผู้รับผิดชอบระบบ/ข้อมูลประเมินจากข้อเท็จจริง
- ฐานกฎหมาย/notice/การส่งต่อ/ผู้รับข้อมูล/อายุเก็บและผู้รับผิดชอบเหตุละเมิดพร้อมใช้สำหรับกิจกรรมที่จะเปิด
- ทำ smoke test หลัง deploy และติดตาม decrypt failure, authorization denial, audit failure, migration mismatch และ notification routing โดยไม่มี PII ใน telemetry

## หลักฐานเมื่อปิดแต่ละงาน

แต่ละ ID ต้องมีผู้รับผิดชอบ, วันที่, commit/PR หรือเอกสาร config ที่เกี่ยวข้อง, test result, การทดสอบข้อมูลเดิม, migration/rollback ที่ใช้, ข้อจำกัด และสถานะของข้อค้นพบเดิม เก็บหลักฐานไว้ใน `outputs/pdpa/evidence/` โดยไม่ใส่ secrets หรือข้อมูลผู้รับบริการจริง

สถานะเริ่มต้น: PDPA-00–13 **ยังไม่เริ่ม**; ขอบเขต sidebar/organization selector ที่แก้ก่อนแผนนี้ **เสร็จแล้วและต้องทดสอบ regression** แผนนี้ไม่ใช่การรับรองว่าปฏิบัติตามกฎหมายครบ การปิดงานต้องอาศัยทั้งผลแก้โค้ดและหลักฐานกระบวนการ/Production ตามแต่ละข้อ
