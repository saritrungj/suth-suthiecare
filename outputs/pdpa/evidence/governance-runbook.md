# กระบวนการหน่วยงานและ PDPA

เอกสารนี้เป็นแนวทางดำเนินงานประกอบ implementation อ้างอิงข้อกำหนดที่ตรวจไว้ใน `outputs/pdpa/requirements.md` และ `security-audit.md` ไม่เลือกฐานกฎหมาย อายุเก็บ หรือข้อยกเว้นแทนผู้รับผิดชอบหน่วยงาน

## Purpose register และประกาศ

จัด register รายหน่วยงาน/กิจกรรม ครอบคลุมการรับบริการ ฟอร์ม ประวัติ งานโรงเรียน การส่งต่อ รายงาน/export, authentication, email/notification และ backup อย่างน้อยต้องมีผู้รับผิดชอบ วัตถุประสงค์ ประเภทข้อมูล กลุ่มเจ้าของข้อมูล ฐานการประมวลผลที่ยืนยัน ผู้รับ/processor การเก็บและสิทธิ์เข้าถึง notice version อายุเก็บและช่องทางใช้สิทธิ

ในแอป System Admin อนุมัติ purpose/notice รายฟอร์มที่หน่วยงานยืนยันแล้ว ผ่าน `PUT /api/pdpa/organizations/:id/purposes/:formId` ไม่มีค่าฐานกฎหมายเริ่มต้น; Production submit ฟอร์มที่ยังไม่มี purpose ที่อนุมัติแล้วจะตอบ 503

หากใช้ฐาน consent ผู้ตอบต้องส่งการยินยอมและ notice version ตรงกับ server ระบบบันทึก evidence พร้อม response ภายใน transaction ข้อความประกาศแต่ละเวอร์ชันอยู่ใน `pdpa_notice_versions` และแก้ข้อความ/ฐานภายใต้ version เดิมไม่ได้ (409); การเปลี่ยนประกาศต้องใช้ version ใหม่

Consent สำหรับการจับคู่เลขบัตรของ guest กับ consent ตาม purpose เป็นคนละ field/วัตถุประสงค์ อย่าใช้ checkbox ตัวหนึ่งแทนทุกกิจกรรม ต้องทบทวนกิจกรรมที่ใช้ข้อมูลสุขภาพ/นักเรียน/ผู้เยาว์กับผู้รับผิดชอบก่อนเปิด และเตรียมการยืนยันผู้แทน/หลักฐานตามนโยบายในกรณีที่ต้องมี; release นี้ไม่ได้อนุมัติ workflow ผู้แทนให้เอง

## การส่งต่อและผู้ให้บริการ

ผู้รับผิดชอบต้นทาง/ปลายทางยืนยันความจำเป็น ข้อมูลสรุปที่แชร์ได้ ผู้รับผิดชอบติดตาม status และข้อตกลงการใช้ข้อมูลก่อน System Admin เปิดคู่ source → destination การปิดคู่หยุดรายการใหม่แต่ยังตรวจประวัติเดิมได้ตามสิทธิ์คู่กรณี

หน้าส่งต่อเป็นการประสานงานสรุป ห้ามใส่คำตอบฟอร์มเต็ม ผลตรวจ เลขบัตรหรือรายละเอียดคลินิกในช่องสรุป แม้ข้อความสรุปเข้ารหัสที่ฐานข้อมูลแล้ว ปลายทางที่มีสิทธิ์ยังอ่านได้; review เนื้อหาก่อนส่ง

Telegram ส่งเฉพาะข้อความมีรายการใหม่และรหัสอ้างอิง การดูรายละเอียดต้องผ่าน login/scope/grants ในระบบ ผู้ดูแลต้องยืนยันสมาชิกกลุ่มและ chat ID ของแต่ละหน่วยงานก่อนบันทึกปลายทาง ไม่มี fallback ไปกลุ่มกลาง

เก็บทะเบียน email/Telegram/hosting/backup providers ที่ใช้จริงพร้อมหน้าที่/ขอบเขต/การเข้าถึง/ปลายทาง/ระยะเก็บ/ข้อตกลง และหลักฐานที่ผู้รับผิดชอบ PDPA ตรวจแล้ว โดยไม่ส่งข้อมูลจริงไปทดสอบผู้ให้บริการ

## การรับคำขอใช้สิทธิ

1. Patient เข้าบัญชี ส่งคำขอเลือกหน่วยงานที่พิสูจน์ความสัมพันธ์ได้ ระบบเก็บรายละเอียดเข้ารหัสและเห็นเฉพาะคำขอตนเอง คำขอจากช่องทางอื่นให้หน่วยงานรับตามช่องทางที่ประกาศและยืนยันตัวตนก่อนเชื่อมกับบัญชี
2. System Admin เลือกหน่วยงาน อ่านคำขอ (mandatory audit) และยืนยันการตรวจตัวตนจริงก่อนสถานะ `identity_verified` อย่าใช้ชื่อเหมือนกันหรือข้อมูล browser เป็นหลักฐานตัวตน
3. ตรวจกิจกรรม/ข้อมูล/หน่วยงานที่เกี่ยวข้อง บัญชีผู้ขอ ผู้แทนเมื่อจำเป็น ข้อยกเว้นและ legal hold; เปลี่ยน `under_review` หลังมีการตรวจ
4. ดำเนินการ access/rectification/portability/restriction/objection/withdrawal/erasure ตามนโยบายที่ยืนยันแล้ว ใช้ audited exports และ secure delivery ที่องค์กรกำหนด; ไม่ส่งผลให้บุคคลอื่นหรือ email/กลุ่มที่ยังไม่ตรวจผู้รับ
5. บันทึกผล/เหตุผล/ผู้ดำเนินการ/หลักฐานแบบจำกัดสิทธิ์ก่อน `fulfilled` หรือ `rejected`; status API ใช้ version check และ immutable events เพื่อป้องกันเปลี่ยนข้ามลำดับ การกด fulfilled ไม่ได้ทำ export/ลบข้อมูล/แจ้งผู้ขอให้อัตโนมัติ
6. ติดตามกำหนดเวลาตามข้อกำหนดที่ผู้รับผิดชอบตรวจไว้และการแจ้งผลตาม notice; หากต้อง withdraw consent ให้เชื่อม evidence ที่เกี่ยวข้องและประเมินผลต่อกิจกรรม/ข้อยกเว้นก่อนดำเนินการ

ห้ามใช้การลบบัญชี login แทนการพิจารณาคำขอ erasure: บัญชีส่วนกลางอาจสัมพันธ์หลายหน่วยงาน จึงจำกัดการลบบัญชีไว้ที่ System Admin และยังรักษาข้อมูลบริการตามกระบวนการที่ต้องพิจารณา

## Retention และ legal hold

นโยบายเป็นรายหน่วยงาน/ประเภทข้อมูล พร้อมผู้อนุมัติ รุ่นและวันที่ ไม่มีจำนวนวันเริ่มต้น ไม่มี automatic deletion การตั้งนโยบายใหม่เก็บ snapshot ใน `pdpa_retention_policy_versions`

API policy รองรับ `form_responses`, `case_logs`, `auth_sessions`, `audit`; preview อัตโนมัติใน release นี้นับ form responses ตามอายุและตัด active legal hold เท่านั้น ประเภทอื่นต้องใช้ register/การตรวจรายการที่ได้รับอนุญาตก่อนงานลบจริง โดยเฉพาะข้อมูลส่วนกลางที่ใช้ร่วมกันหลายหน่วยงาน

ก่อนตรวจ/lบข้อมูล: ยืนยัน purpose/อายุเก็บ ข้อมูลสุขภาพที่ต้องรักษา ความสัมพันธ์กับหน่วยงานอื่น ข้อจำกัดจาก incident/ข้อพิพาท และ backup lifecycle ตั้ง hold ราย response ผ่าน `PUT /api/pdpa/organizations/:id/legal-holds/:responseId` กับ `{held:true}` ก่อนเปลี่ยน policy เมื่อ release hold ต้องมีหลักฐานการอนุมัติ

`POST /api/pdpa/organizations/:id/retention/dry-run` คืน candidate count และ policy version ไม่มีค่าข้อมูลจริงและไม่ลบ ให้เจ้าของข้อมูลตรวจรายการ/ความสัมพันธ์ในพื้นที่จำกัดสิทธิ์ก่อนเสนอแผนลบที่ review ได้ งานลบ Production แยกจาก implementation นี้

## Incident runbook และการซ้อม

1. รับเหตุจาก telemetry/audit/notification/migration/readiness หรือบุคลากร กำหนด incident ID ผู้รับผิดชอบระบบ/DB/PDPA และช่องทางติดต่อที่ยืนยัน
2. กักกันตามเหตุ: ปิด business writer/notification/referral pairs, revoke sessions/invitations, จำกัด network หรือบัญชีที่เกี่ยวข้อง โดยรักษาบริการที่จำเป็นตามแผนองค์กร ไม่เปิด bypass เพื่อแก้ 503
3. เก็บหลักฐานที่จำเป็นในพื้นที่เข้ารหัสและจำกัดสิทธิ์: เวลา request IDs metadata audit/counts release/schema/key IDs/checkpoints และลำดับการดำเนินการ ห้าม copy plaintext ผู้รับบริการลง chat/repo/error log และรักษา chain of custody
4. ผู้รับผิดชอบ PDPA ประเมินขอบเขตข้อมูล/ผู้ได้รับผลกระทบ/ผู้รับ/ความเสี่ยงและหน้าที่แจ้งตามข้อกำหนดที่ตรวจไว้ในรายงาน บันทึกผลและเวลา; กำหนดผู้อนุมัติและผู้แจ้งจริง ไม่ให้นักพัฒนาส่งข้อความภายนอกเอง
5. แก้เหตุ ทดสอบ restore/readback/key/audit/scope/session ก่อนเปิด traffic ทบทวนว่า session/invitation ที่เพิกถอนต้องไม่กลับมาใช้ได้จาก restore
6. ซ้อมด้วยข้อมูลจำลองอย่างน้อยเหตุ audit storage unavailable, key ผิด/สูญหาย, cross-unit access attempt, OTP provider unavailable และ backup restore เก็บผู้เข้าร่วม เวลาตอบสนอง ผลที่คาด/จริง และงานแก้หลังซ้อม

ก่อน Production ให้เติม incident contacts, ผู้มีอำนาจตัดสินใจ ช่วงเวลา/ช่องทางแจ้งที่ผู้รับผิดชอบยืนยันแล้ว และ reference ไปหลักฐานซ้อม ไม่ใส่เบอร์หรือข้อมูลส่วนบุคคลใน repo สาธารณะ
